### `lucia_control` — open-loop `/odom`, ahead of the cable fix

The Roomba's sensor replies still don't reach the Pi (confirmed last session,
2026-09-18), which was blocking `/odom`. Decided not to wait on that: `/odom` can
be *estimated* from the wheel speeds `roomba_bridge.py` already commands, rather
than measured from encoder feedback. This is a real tradeoff, not a free win — it
can't notice slipping, stalling, or a collision, so it will drift more than real
encoder feedback would. It's still a better input to `slam_toolbox` than assuming
the robot never moves, and the option of switching to real encoder data later,
once the cable's fixed, was a deciding factor: it's a drop-in replacement, not a
redesign.

Added:
- `odometry.py` — pure dead-reckoning math (differential-drive kinematics,
  integrated along the arc each tick actually follows, not a straight-line
  approximation). Takes left/right wheel speed + elapsed time, returns
  (x, y, heading). Deliberately **does not care** whether those wheel speeds were
  measured or commanded — that choice is the caller's. 17 unit tests.
- `roomba_bridge.py` now publishes `nav_msgs/Odometry` on `/odom` and broadcasts
  the matching `odom`→`base_link` TF transform every drive tick, feeding
  `odometry.py` the same commanded speeds it just sent to the wheels (not a
  sensor reading — see above). New parameters: `odom_frame_id` (default `odom`),
  `base_frame_id` (default `base_link`).
- Covariance fields on the `/odom` message are deliberately left at zero rather
  than filled with invented numbers — the true uncertainty of a commanded-not-
  measured estimate isn't known yet.

**Notably, this needed no new hardware constants.** Converting raw encoder ticks
to millimeters needs wheel diameter and counts-per-revolution — both still
unmeasured on the new motors. Working from commanded mm/s instead skips that
conversion entirely; the only number `odometry.py` needs is the wheel spacing
(235mm), which was already a real measured value in use elsewhere in the repo.

Tested on a laptop first, with stand-ins for ROS2 and the Roomba (no rclpy
available there):
- All 20 `pytest` unit tests pass (`motion.py` + `odometry.py`)
- A scripted run of the actual node logic against fake ROS/Roomba objects confirms:
  driving straight accumulates the right distance, spinning in place changes
  heading without moving x/y, the TF transform matches the `/odom` message, and
  custom frame-name parameters are honored

### On-robot test, same day

With both the Roomba and lidar plugged into the Pi this time (first time testing
both together), WiFi switched from the Pi's own access point to a home network so
SSH wasn't tied to the AP during testing (see "Network" below).

**`/odom`: works as designed.** Drove around with `teleop_twist_keyboard`, mixing
forward motion and turns, and `/odom` tracked both the position change and the
heading change correctly. Confirms the open-loop approach does what it's supposed
to: reflect exactly what was commanded, nothing more.

**Lidar: needed one real fix.** `ros2 pkg executables rplidar_ros` showed the
executable is `rplidar_composition`, not `rplidar_node` as assumed when
`rplidar.yaml` was written — though the *node* it creates at runtime is still
named `rplidar_node`, so the config file's settings were already targeting the
right thing; only the "how to launch it" comment in the file was wrong.

First real attempt connected fine (got serial number, firmware version, a healthy
status) but then failed: `Cannot start scan: '80008000'` / `Failed to set scan
mode`, and the lidar's motor never spun up. Isolated the cause by testing the old
Python driver (`lidar_reader.py`) directly, outside ROS2 entirely — it successfully
got a real 60-point scan on the same hardware, same cabling, same session,
confirming the lidar itself and its wiring were fine. The problem was specific to
the ROS2 driver.

Root cause: the ROS2 driver's own default scan mode isn't compatible with this
lidar's older firmware (Hardware Rev 5, Firmware 1.25). `rplidar.yaml` already
had `scan_mode: Standard` set, but that hadn't been exercised yet — setting it
explicitly fixed the failure immediately. Confirmed three ways: by hand with
`-p scan_mode:=Standard`, then by loading the actual `rplidar.yaml` file via
`--params-file`, then checking `/scan` was actually publishing
(`ros2 topic hz /scan` → ~11.7 Hz, consistent with the lidar's normal spin rate).

### Network

Switched the Pi from broadcasting its own WiFi to joining a home network
(hidden SSID, needed `nmcli connection add` + `802-11-wireless.hidden yes` rather
than the simpler `nmcli device wifi connect`, which can't work out the security
type for a hidden network on its own). Undo: `sudo nmcli connection up pi-ap` +
`sudo systemctl start dnsmasq`.
