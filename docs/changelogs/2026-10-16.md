## Decisions

### Autonomous mapping is the goal; keyboard driving is only a test tool

Keyboard teleop exists to check one piece at a time (wheels, then whether
`slam_toolbox` builds a sensible map). It is not how the robot is meant to run, and
workflow/tooling should be built around the autonomous run, not around teleop.

### SWEEP mode first, frontier exploration later

- **SWEEP** (port of `slam_avoid_server.py`'s sweep logic): drive straight; when
  something's ahead, spin toward the clearer side until the front is clear;
  repeat. Needs only `/scan`, no encoders, so it works with today's open-loop
  `/odom`.
- **Frontier exploration** (Nav2 + `m-explore-ros2`): heads for unmapped areas
  instead of bouncing around. Kept as a feature for later; it needs real encoder
  odometry first.

Order: map works → safety stop, tested alone → SWEEP → one launch file (plus
Docker Compose) that starts everything. The 2026-10-09 reason for this order
still holds: the safety stop shouldn't go live for the first time at the same
moment as autonomous driving.

### Safety stop will use the ToF sensors, not the lidar

The team is building VL53L5CX ToF distance sensors on a Pico (`src/tof_pico/`).
The safety stop will be built on those once they're ready, so it's on hold until
then. SWEEP still comes after it.

### Better maps: IMU first, encoders when the cable is fixed

The first map's doubled wall came from heading drift. The IMU fixes heading
directly and was ready today; the encoders are blocked on the Roomba's broken
reply line (see the IMU section). Both together is the end goal.

### Web control page revived

The web panel was deferred on purpose on 2026-10-09. With mapping working end to
end, it was revived on request: running the robot meant juggling three SSH
terminals and long commands. It's a deliberate decision, not bundled into
something else.

## Work Completed

### `lucia_lidar` — launch file fixes (made before the first run, then confirmed on the Pi)

- **slam_toolbox would never have started mapping.** In Jazzy it's a lifecycle
  node: it starts idle and has to be configured and activated. The launch file
  started it as a plain `Node`, so it would have run but done nothing. It now
  includes the package's own `online_async_launch.py`, which does those steps.
  This also removes the unverified `async_slam_toolbox_node` executable-name
  guess. `use_sim_time` is passed as `false`, since that launch file defaults it
  to `true`.
- **Every scan would have been dropped.** Nothing published the `base_link`→`laser`
  transform, so `slam_toolbox` couldn't relate a scan to the robot. Added a static
  transform publisher. Its rotation is the `laser_yaw` launch argument, default π:
  last semester's code treats the lidar's own 0° mark as robot-forward, and
  `rplidar_ros` reports that direction at 180° in its frame. Not yet verified;
  the lidar's x/y offset from the robot's center is not measured yet (0 for now).
- **`scan_check`** (`ros2 run lucia_lidar scan_check`): prints the closest
  reading's distance and angle once a second. With a box in front of the robot,
  it shows whether `laser_yaw` should stay at π (about ±180°) or be 0 (about 0°).
- Added `setup.cfg` to `lucia_lidar` (the same fix `lucia_control` needed on
  2026-09-18 for `ros2 run` to find its executables).

### On-robot test: first real map

Run on the Pi the same day, over WiFi (Pi joined the shared network, hotspot off):

- **Devices:** the udev rules already existed: `/dev/rplidar` → `ttyUSB0`
  (Silicon Labs CP2102) and `/dev/roomba` → `ttyUSB1` (FTDI FT232R). The two adapters
  use different chips; `docs/setup/ros2-pi.md` assumes both are CP210x.
- **Build:** `colcon build` fails on `lucia_vision` (Jetson/ZED package, needs CUDA)
  and then skips `lucia_bringup`. Use `--packages-skip lucia_vision` on the Pi.
- **Lidar driver froze once** right after `Start`: the motor spun, but no `/scan`
  appeared and Ctrl+C was ignored. Ctrl+\ and a rerun fixed it, and it didn't
  happen again. A powered USB hub is in use, so it isn't the Pi 5's USB current
  limit.
- **`scan_check`:** a hand in front of the robot read about -170° and a hand on
  its left about -92°: a plain 180° turn, not mirrored. The default
  `laser_yaw` (π) is right.
- **Bench (robot still):** slam_toolbox configured, activated, and once
  `roomba_bridge` was publishing `odom`→`base_link` it took the scans and saved a
  map. Only a small starburst near the robot was filled in: a stationary robot
  gives slam_toolbox one scan, and it leaves cells unknown until a ray has crossed
  them at least twice.
- **Driving (keyboard, about 0.15 m/s):** `room1.png` shows a recognizable room,
  about 2.6 × 2.9 m, with straight walls, clear corners and an opening on one side.
  One wall shows up doubled (about 20-30 cm apart), most likely heading drift from
  the open-loop `/odom`.
- **Found along the way:** after the Roomba is turned off and on, `roomba_bridge`
  has to be restarted. Its heartbeat re-sends Safe (131), which a freshly
  powered-on Roomba ignores without Start (128) first. Added to TODO.md.

### IMU: Ling's BNO08X fused into mapping

- **Encoder check first:** counting bytes, not decoding them, showed **zero bytes**
  come back from the Roomba for battery or encoders, while a beep command played,
  so the Roomba was awake and receiving. Only the Roomba-to-Pi direction is broken.
  The encoders themselves are untested. That made the IMU the quicker way to fix
  heading drift.
- **Pico:** Ling's BNO08X is on a Pico 2 (address `0x4A`, ADD pin to GND), plugged
  into the Pi over USB. `src/imu/stream_main.py` (uploaded as the Pico's `main.py`)
  streams the game rotation vector + gyro as `I,qw,qx,qy,qz,gx,gy,gz` lines at about
  50 Hz. It was loaded straight from the Pi with `mpremote` (installed via `pipx`);
  that Pico had a ToF `main.py` on it, backed up to `~/tof_main_backup.py` on the Pi.
  udev: `/dev/imu`, matched by the Pico's serial number.
- **`lucia_imu` / `imu_bridge`:** publishes `/imu/data`. On the Pi: 50 readings/s,
  0 bad lines; a quarter turn left by hand read +94.7° and returned to about +1-2°.
- **Fusion:** `robot_localization` EKF (`lucia_bringup/config/ekf.yaml`) takes forward
  speed from `/odom` and heading + turn rate from the IMU, and publishes
  `odom`→`base_link`. `roomba_bridge` gained `publish_tf` and now fills in `/odom`'s
  twist. `ros2 launch lucia_bringup mapping.launch.py` starts everything except
  teleop (`use_imu:=false` for the wheels-only setup).
- **Docker image rebuilt** with `ros-jazzy-robot-localization` and a colcon
  defaults file, so plain `colcon build` skips `lucia_vision`.
- **Result:** `room2.png`, with the IMU, has single thin walls and square corners;
  `room1.png` (wheels only) had a doubled wall and a skewed outline. Not a
  controlled comparison (one run each, different starting heading), but the

### Web control page and Docker Compose

- **`lucia_web` / `web_ui`** (new package) serves the control page on port 8080:
  - status lights: Mapping, Lidar (`/scan`), IMU (`/imu/data`), Wheels (`/odom`),
    and the browser's connection
  - Start / Stop mapping (runs `ros2 launch lucia_bringup mapping.launch.py` as a
    child process; "Use IMU" checkbox = `use_imu`), with the launch output shown
    on the page
  - live map (polls `/map` every 2 s) with the robot's position from TF
    (`map`→`base_link`)
  - hold-to-drive pad + arrow keys/WASD, max 0.15 m/s and 0.6 rad/s. The page
    re-sends every 100 ms while held; if that stops for 0.3 s (released, tab
    closed, WiFi dropped) the node sends one stop, and `roomba_bridge`'s 0.5 s
    `/cmd_vel` timeout is the second layer
  - save map (runs `map_saver_cli` into `/maps`, i.e. `~/maps` on the Pi), list
    and download saved PNGs
  - plain `http.server`, so no new packages and no image rebuild
- **Tests:** `logic.py` and `mapping_process.py` have 24 pure-Python tests; the
  HTTP endpoints were smoke-tested here with ROS stubbed out.
- **`docker/compose.yml`:** runs the container in the background with
  `restart: unless-stopped`, so it comes up at every boot; it runs `colcon build`
  then `web_ui`. All of `/dev` is shared with device-type rules (`c 188:*`
  ttyUSB, `c 166:*` ttyACM) instead of `--device` flags, so a device unplugged at
  boot doesn't stop the container from starting, and replugging works.
- **On the Pi:** `docker compose -f docker/compose.yml up -d`, page opened from the
  laptop, mapping started, driven and saved from the browser. Confirmed working.

### Late evening: first Explore on the robot

Pulled `dev` on the Pi and restarted Compose: 6 packages built, `web_ui` came up
(so `nav2_msgs` is installed), and after Start mapping, Explore was enabled and
Nav2 planned a path, so all four Nav2 servers started under the expected names.

The routes were bad: the planned path left the room through a gap in the wall,
went around the outside through unmapped space, and the robot got stuck. Two
causes, both fixed (not yet re-run):
- NavFn had `allow_unknown: true`, so unseen space counted as drivable when the
  mapped way was blocked. Now `false`: plans use mapped floor only.
- Frontiers were ranked by straight-line distance and kept even when nothing
  connected them to the robot. Now a flood fill from the robot over mapped floor
  at least 0.2 m from walls (`clearance_m`, was 0.25 for goals only) decides
  which frontiers count, the goal is a reached cell, and ranking uses that
  driving distance. New tests cover a frontier behind a wall and one reachable
  only through unknown space.

### Network and Pi tooling notes

- **Two network modes.** At boot the Pi runs its own hotspot (`pi-ap`, SSID
  `lucia-control`, Pi at `10.42.0.1`, no internet). Today it was switched onto a
  shared WiFi for internet (git pull, image rebuild), from an Ethernet SSH session
  so the connection survived the switch:
  `sudo systemctl stop dnsmasq && sudo nmcli connection up <wifi>`. Stopping
  `dnsmasq` matters: left running, it hands out addresses on the shared network.
  Back to the hotspot: reboot, or
  `sudo nmcli connection up pi-ap && sudo systemctl start dnsmasq`.
- **`mpremote`** is installed on the Pi (`pipx install mpremote`) for loading code
  onto the Picos from the Pi. It can't interrupt the IMU Pico while it streams
  (it hung trying); replug the Pico afterwards so `main.py` runs again.
- **Pasting tips over SSH:** paste `docker run` on its own and wait for the
  container prompt before pasting the next commands (lines pasted together got
  dropped). A stray `[200~` at the start of a pasted command is a terminal paste
  glitch; retype it.
