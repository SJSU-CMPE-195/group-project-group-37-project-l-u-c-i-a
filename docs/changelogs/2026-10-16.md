## Decisions

### Autonomous mapping is the goal; keyboard driving is only a test tool

Keyboard teleop exists to check one piece at a time (wheels, then whether
`slam_toolbox` builds a sensible map). It is not how the robot is meant to run, and
workflow/tooling should be built around the autonomous run, not around teleop.

### SWEEP mode first, frontier exploration later

- **SWEEP** (port of `slam_avoid_server.py`'s sweep logic): drive straight; when
  something's ahead, spin toward the clearer side until the front is clear;
  repeat. Needs only `/scan`, no encoders, so it works with today's open-loop
  `/odom`.
- **Frontier exploration** (Nav2 + `m-explore-ros2`): heads for unmapped areas
  instead of bouncing around. Kept as a feature for later; it needs real encoder
  odometry first.

Order: map works → lidar safety stop, tested alone → SWEEP → one launch file (plus
Docker Compose) that starts everything. The 2026-10-09 reason for this order
still holds: the safety stop shouldn't go live for the first time at the same
moment as autonomous driving.

## Work Completed

### `lucia_lidar` — launch file fixes (not yet run on the Pi)

- **slam_toolbox would never have started mapping.** In Jazzy it's a lifecycle
  node: it starts idle and has to be configured and activated. The launch file
  started it as a plain `Node`, so it would have run but done nothing. It now
  includes the package's own `online_async_launch.py`, which does those steps.
  This also removes the unverified `async_slam_toolbox_node` executable-name
  guess. `use_sim_time` is passed as `false`, since that launch file defaults it
  to `true`.
- **Every scan would have been dropped.** Nothing published the `base_link`→`laser`
  transform, so `slam_toolbox` couldn't relate a scan to the robot. Added a static
  transform publisher. Its rotation is the `laser_yaw` launch argument, default π:
  last semester's code treats the lidar's own 0° mark as robot-forward, and
  `rplidar_ros` reports that direction at 180° in its frame. Not yet verified;
  the lidar's x/y offset from the robot's center is not measured yet (0 for now).
- **`scan_check`** (`ros2 run lucia_lidar scan_check`): prints the closest
  reading's distance and angle once a second. With a box in front of the robot,
  it shows whether `laser_yaw` should stay at π (about ±180°) or be 0 (about 0°).
- Added `setup.cfg` to `lucia_lidar` (the same fix `lucia_control` needed on
  2026-09-18 for `ros2 run` to find its executables).

All of this is syntax-checked only; this laptop has no ROS2.
