## Work Completed

### `lucia_control` — written

- `roomba_oi.py` (the existing Roomba serial driver) copied into the package, since
  the Pi's Docker container only mounts `src/ros2`, not `src/scripts`
- `motion.py` — pure math converting a `/cmd_vel` command (forward speed + turn rate)
  into left/right wheel speeds; 11 unit tests
- `roomba_bridge.py` — the ROS2 node itself:
  - Subscribes to `/cmd_vel`, drives the wheels via `drive_direct()`
  - Runs the Roomba in **Safe mode** and re-sends that command every second (a
    heartbeat), so it recovers on its own after being picked up — no restart needed.
    Chosen because the bump sensor has been physically removed from this robot, and
    the old scripts needed a full restart after every pickup.
  - Stops the wheels if `/cmd_vel` goes quiet for 0.5s, since the Roomba would
    otherwise keep driving at the last speed forever
  - `oi_mode:=full` parameter exists only for bench testing on blocks (Safe mode
    treats wheels in the air as a wheel-drop and cuts the motors)
- `docker/Dockerfile` for the Pi's ROS2 Jazzy container — adds `python3-serial`
  (needed by the driver) and `ros-jazzy-teleop-twist-keyboard` (for driving it
  manually over SSH) to the existing `rplidar_ros` / `slam_toolbox` / `nav2_bringup`
  install list

### Bug found and fixed: `ros2 run` couldn't find the node

First build on the Pi succeeded but `ros2 run lucia_control roomba_bridge` reported
"No executable found." The package was missing `setup.cfg`, which tells
`ament_python` to install console-script launchers to `lib/lucia_control/` instead of
the default `bin/` — without it, `ros2 run`'s search path never finds them. Fixed by
adding `setup.cfg`; confirmed working after a rebuild.

### On-robot test

With the lidar unplugged (Roomba as `/dev/ttyUSB0`, no udev rules yet):

1. Built the container on the Pi (`docker build`, ~8 minutes over ethernet — the
   Pi's own WiFi has no internet)
2. Ran `roomba_bridge`, drove it with `teleop_twist_keyboard` over a second SSH
   session

**First attempt: nothing moved, in either Safe or Full mode.** Spent a while
suspecting the (now-missing) cliff sensor or a bug in the node, before testing with
a bare Python script (no ROS) — which *did* move the robot. That isolated the fault
to something other than the new code.

**Root cause: an old service was already holding the Roomba.** `lucia.service`
(running since May, auto-started at boot) runs the old web control panel
(`slam_avoid_server.py`) on the same serial port and GPIO pins. It was fighting
`roomba_bridge` for the Roomba over the same cable. `sudo systemctl stop lucia`
before testing fixed it immediately.

**After that: full on-robot pass.**
- Drives forward/back/turn correctly from the keyboard, over SSH
- Stops within ~0.5s of `/cmd_vel` going quiet
- Picked up mid-drive → stops. Set back down → resumes driving on its own, no
  restart. (This was the whole point of the Safe-mode heartbeat.)

### Pi cleanup

At the user's request, with the above service conflict as the motivating case:

- `sudo systemctl disable --now lucia` — the old web control panel no longer starts
  at boot (it had been running unattended since May). Still runnable by hand with
  `sudo systemctl start lucia`; stop it again before any ROS2 test.
- `sudo nmcli connection modify pi-ap connection.autoconnect-priority 100` — the
  Pi's own WiFi access point (`lucia-control`) now wins over saved networks at boot,
  confirmed with a real reboot test.

### Checked, not fixed: the Roomba's sensor replies still don't reach the Pi

Read battery voltage directly: came back `0`, which a real battery can't report.
Confirms the cable problem noted back in March (`src/scripts` era) is still present
on the new wheel motors. Driving still works fine (that direction of the cable is
fine) — this only blocks reading anything *back* from the Roomba: encoders,
battery, cliff/wheel-drop sensor state over serial.
